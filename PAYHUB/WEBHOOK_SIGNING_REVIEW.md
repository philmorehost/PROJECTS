# Merchant webhook signing consistency follow-up

## Source finding and bounded change

A follow-up to the historical VTU PayHub outage review confirmed that the generic sender and admin retry already selected test/live keys correctly. Two other paths still differed:

- `verify.php` preferred the live merchant key even for test transactions and fell back to the test key if the live key was absent.
- `webhook-paystack.php` selected the appropriate mode key but fell back to a global `payhub_webhook_secret` with default `secret` when the merchant key was missing.
- All four paths could attempt unsigned delivery when no signature was available.

All four now use `includes/webhook-signing.php`. It accepts only known database boolean/0/1 mode representations, checks charge.success payload domain against the persisted mode, and computes HMAC-SHA256 over the exact raw body using only that merchant's corresponding key. No opposite-mode/global/default fallback. Missing/invalid key, unknown mode, invalid JSON/event or mismatched domain refuses signing. The sender then skips HTTP and records the existing failed-delivery outcome with HTTP 0 and a generic signing-refused diagnosis. HTTP 0 here is a local refusal, not a merchant HTTP response. Fix the exact mode key or investigate the stored payload; do not relabel a test transaction as live to retry it.

No wallet amounts, balances, ledger writes, payload amount units, historical payloads, transaction statuses, delivery-log schema or receiver activation switches are changed. In particular, the verify-page's legacy NAIRA payload versus other senders' KOBO payload remains an explicit separate compatibility issue. This signing change must not be described as an end-to-end funding repair.

## Regression evidence

`php PAYHUB/tests/webhook_signing_test.php` covers mode/key isolation, raw-byte signatures, invalid/missing keys and payloads, shared-secret refusal and the actual four sender refusal blocks with a network-init trap. 89 fixture-only checks pass locally in PHP-wasm; all five changed PHP implementation files parse there. A dedicated native PHP 8.2/8.3 CI workflow runs parser and regression checks. No test contacts a provider, database or merchant.

This is not full endpoint/MySQL/provider integration. Existing curl/TLS behaviour, sender transaction boundaries, delivery durability/retries, historical amount compatibility and receiver gates require separate validation. Missing-key and domain-mismatch deliveries previously sent unsigned or with a fallback key now fail deliberately rather than appearing delivered. Deploy the new helper with/before the updated shared functions and sender files, never omit it from update packages. No migration is needed for this change.

## Next increment: additive amount-unit contract

Newly generated payloads from the generic sender, Paystack forwarding and browser verify-page now declare `money_contract_version: 1`, `amount_unit` (`major`/`minor`) and `amount_basis` (`requested`/`gateway`) inside `data`. Existing amount values and types are unchanged:

| Sender | Legacy `amount` | New declaration |
| --- | --- | --- |
| Generic | Integer kobo; gross paid when known, otherwise its existing requested fallback | `minor`, `gateway` when known; `requested` for fallback |
| Paystack forwarding | Gross paid integer kobo | `minor`, `gateway` |
| Browser verify | Requested naira, preserving the stored value/type | `major`, `requested` |

Browser verify now also includes the stored currency. Its `amount_kobo` requested-value alias remains. The common requested/gateway/fee/settled fields retain their existing kobo conversion and values. This does NOT repair or endorse generic historical rows whose gateway_amount is actually the existing requested fallback: the label explicitly identifies the lack of a known paid amount. Recipients must independently verify payment rather than treat the labels or the requested value as payment evidence. No currency conversion, rounding policy or wallet accounting is changed.

The API reference now explains sender differences, the fallback caveat, raw-byte mode-specific verification, common minor-unit fields and independent verification/idempotency requirements. Verification API semantics are unchanged. Original stored retry bodies are not relabelled or re-encoded. Old unlabelled payloads remain signable under the previous mode/domain rules; recipients must not infer units from magnitude or blindly replay historical events.

`webhook_money_contract_test.php` evaluates the actual three shipped payload-builder expressions (not hand-copied alternatives) with isolated fixtures and the shipped conversion function: tiny/fractional/large requested amounts, test/live modes, known/missing generic paid amount, upstream label override resistance, exact legacy value/type preservation, common kobo fields, currency, signature coverage and historical retry-byte preservation. 181 local PHP-wasm checks pass, with no database/network/provider. Native PHP 8.2/8.3 CI now runs both suites. This increment improves the migration contract; a breaking unification of legacy amount or replacement of delivery durability/transaction boundaries is still not implemented or authorized for activation.

## Delivery durability prerequisite: compatible log schema

The runtime `ensure_critical_tables()` fallback previously created the obsolete `(user_id, event_type, response_code)` log shape. Current senders/admin use `(transaction_id, status, attempt_count, last_attempt_at, payload, response)`. `CREATE TABLE IF NOT EXISTS` cannot repair an existing legacy table, and swallowed logging failures can leave a delivered webhook with no usable delivery record. This is a source-confirmed compatibility gap, not proof of any specific live installation's schema.

The runtime fallback now creates the current column contract for a missing table, including a transaction lookup index. Existing installations require the explicit operator migration `install/20261118_webhook_log_compat.sql`. It is additive and rerunnable: it creates a missing table, adds only absent columns and a lookup index, and does not rewrite existing definitions or records. It does not run from a web request, bump the general runtime schema marker or alter wallet/transaction tables. There is no automatically applied schema migration here.

Back up and review `SHOW CREATE TABLE webhook_logs` first; select the correct database and run outside application transactions in a maintenance window because MySQL DDL implicitly commits and acquires metadata locks. Rehearse on a sanitized clone. Unknown legacy transaction IDs, status, attempt counts, last-attempt timestamps and responses stay NULL rather than inventing a link or an outcome. Original payloads, response_code, user_id, event_type and timestamps are preserved. Existing conflicting column definitions/constraints or custom index names require operator review rather than a destructive ALTER. Rerunning is safe for supported shapes but concurrent migration runners are not supported. No rows are deleted and no foreign keys/engines are modified.

The existing admin inner join still intentionally excludes records without an authoritative transaction link; these preserved legacy rows must be examined with restricted read-only database tooling and reconciled independently. Do not infer links from metadata/email or replay old rows to manufacture delivery records. Existing installer foreign-key deletion behaviour is not changed by this patch.

`webhook_log_schema_mysql_test.php` runs only with a disposable-CI guard and creates/drops its own randomly named database. It exercises the actual shipped runtime and installer DDL plus the operator migration against legacy, current, runtime-created and missing schemas; reruns migration; preserves historical columns/bytes; and verifies current sender inserts and admin-style retry joins/updates. This is schema compatibility evidence, not provider/network/crash recovery validation. The separate native MySQL CI job supplies its own disposable database; the local PHP-wasm environment is used only for parsing this MySQL test, not claimed as MySQL execution.

Still remaining: persist-before-send/outbox semantics, serialized retry claims, ambiguous HTTP outcome handling and crash recovery. Current senders still log after HTTP and some perform outbound delivery inside accounting transactions. This schema fix does not make delivery exactly-once, durable across those crash windows, or safe for blind automatic retries. No automatic retry worker or financial activation is enabled.

## Manual retry serialization and uncertain outcomes

`admin/webhooks.php` now uses `includes/webhook-retry.php` with an operator-applied additive `install/20261118_webhook_retry_claims.sql` table. Apply the prior log-schema repair first, outside application transactions, after backup/review. Deploy the helper with the page. No web-request DDL or automatic retry worker is added. Missing/non-InnoDB claim, log, user or transaction tables fail closed; existing log listing remains accessible if the claim migration is absent.

The admin must still be authenticated, authorized and pass CSRF. Each request also requires an explicit independent-reconciliation confirmation that the merchant has not already credited the payment. This is an operator attestation, NOT machine proof of non-credit. The helper rechecks the locked successful transaction, failed linked log, exact stored reference/domain, corresponding merchant signing key and canonical HTTPS destination. Any already acknowledged sibling log blocks replay. The unique claim primary key is the transaction ID, so two logs for the same payment cannot create two admin retries. The transaction-wide claim and attempt increment commit before any HTTP. No database transaction is held open during merchant HTTP. URL redirects and non-HTTPS protocols are disabled on this path; TLS checks remain enabled. This is not a comprehensive SSRF/DNS-rebinding remediation for merchant URLs.

The claim preserves the prior response/status/attempt count/timestamp and records the exact payload/destination hashes. Original stored payload bytes are posted and signed without relabelling. Claim state starts `attempting`. Only transport-success plus HTTP 2xx becomes `succeeded`; other results (including 3xx, 4xx, 5xx, timeout, connection failure) become `unknown`. Non-2xx does NOT prove the merchant did not commit a credit. A crash or completion-database failure leaves the claim blocked in `attempting`. Completion is a token-owned compare-and-set, atomically committed with the log outcome; late or non-owning completions cannot overwrite a final result. Attempt count is incremented once at reservation, not again on completion.

No claim expires, and there is deliberately no reclaim/delete/reset button or command. Both `attempting` and `unknown` require independent reconciliation, and `succeeded` is not replayable. Do not delete claims, change IDs/statuses or create another log/transaction to circumvent them. This conservative increment allows at most one claimed ADMIN retry per payment, not unlimited retries after known rejections. Future reconciliation tooling requires its own reviewed authorization/evidence design. Claim state and pre-retry snapshots are evidence; existing claim rows must survive transaction/log cleanup (there are no cascading foreign keys in this new table). No such cleanup is performed.

`webhook_retry_mysql_test.php` exercises the real helpers in a disposable native MySQL database, including six independent competing PHP processes over two log IDs, committed reservation visibility, missing/nontransactional schema rejection, acknowledgement requirements, preflight failures, sibling success refusal, signature/domain checks, raw bytes and prior-history preservation, nonowner/stale completion, 2xx versus uncertain results, process-death simulation and rollback on changed delivery records. It performs no merchant HTTP or provider/database production access. Local PHP-wasm runs parse this test only; native CI executes MySQL/process tests.

Scope boundary: first-delivery senders do NOT yet use this claim table and can still send/log within or after their existing accounting transactions. This does not serialize automatic initial sends against admin retries, provide a universal outbox, repair already-lost delivery logs, or prove exactly-once merchant credit. Existing user/transaction policy changes after the short claim snapshot are also not an atomic authorization boundary with the remote server. Keep independent receiver verification, tenant/account matching and durable merchant idempotency. Provider activation, historical credit/replay, automatic ambiguous retry and financial holds remain unchanged.

## Protected generic initial delivery — follow-up after PR #282

The shared `trigger_merchant_webhook()` sender now uses `includes/webhook-initial.php` to commit the exact payload log and an exclusive claim BEFORE merchant HTTP. It requires the log-schema migration, retry-claims migration, then `install/20261118_webhook_initial_claims.sql` (adds `delivery_kind`, preserving existing claims as `admin_retry`). This is operator-applied DDL only. A missing migration/unsupported engine refuses HTTP; there is no fallback to the previous unclaimed sender. Deploy both helpers with the shared functions file. No live migration or activation is performed here.

The helper refuses caller-owned accounting transactions rather than committing them, locks/rechecks the successful payment and exact named snapshot fields (including amounts/mode/account/merchant/key/destination), requires a reference/domain-bound signature and HTTPS destination, and refuses any existing linked log. A new exact-body log and `initial` claim are committed atomically before HTTP. The shared transaction-ID primary key also blocks competing protected generic calls and admin retries. A failed claim rolls back its new log. Generic cURL explicitly verifies TLS and disables redirects/non-HTTPS protocols. Completion reuses token-owned atomic finalization; failed completion or process death leaves a durable blocked claim and payload, not an invisible sent request. Non-2xx/transport uncertainty is never automatically retried. Initial attempts consume the same permanent claim slot as an admin retry: there is deliberately no admin override/reset route, even after known HTTP failure.

This closes the unlogged-send window for the generic sender, not every funding/delivery window. A crash AFTER accounting commit but BEFORE this function claims can still leave a successful payment with no queued notification: this is NOT a full transactional outbox or dispatch worker. It does not reconstruct missing historical logs, infer that absence of a log proves non-delivery, scan historical transactions or replay them. Existing callers and merchant independent verification/idempotency remain important. No lost historic evidence can be recovered from this code change.

The other initial senders in `webhook-paystack.php` and `verify.php` are NOT integrated in this increment and can still race each other or a protected sender/retry. Their accounting-transaction ordering needs a separately reviewed integration; do not describe the system as globally exactly-once. Shared claimed admin/generic requests are serialized only. Missing-key preflight still makes no merchant call. This work changes no ledger, payment amount, net settlement, provider gate or historical record.

Native MySQL tests now also cover missing-initial-migration rollback, preservation of a caller's active transaction, stale snapshots, exact initial body visibility on another connection, initial-versus-admin exclusion, interrupted initial claims, existing-log rejection, successful shared finalization, migration reruns and six independent competing initial-delivery processes. Existing money/signing suites continue to pass locally. These tests issue no merchant HTTP or provider calls.

## Paystack forwarding joins protected initial delivery — follow-up after PR #283

After accounting has committed, Paystack forwarding now reloads the current payment/merchant snapshot and checks its outgoing reference, status, currency, receiving account and all five money fields against persisted settlement evidence. Missing stored evidence or mismatches refuse HTTP rather than reconstructing amounts. `payhub_forwarded_payload_matches()` uses the existing minor-unit conversion policy. It does not recalculate fees, alter ledger/accounting, change payload units or prove provider settlement on its own; existing upstream signature/mode and fulfilment checks remain mandatory.

Forwarding then uses the SAME exact-body initial log/claim helper and shared transaction-ID claim table as the generic sender/admin retry. The exact payload/log commits before HTTP, and token-owned completion records acknowledged or uncertain outcomes. Endpoint/key changes are bound to the reloaded snapshot and rechecked under lock; forwarding uses the claimed snapshot destination/signature rather than the earlier email-notification snapshot. HTTPS/TLS enforcement and no redirects match the protected generic path. Claim/schema/HTTP/completion errors never roll back already-committed accounting or fall back to unclaimed delivery; they produce a generic restricted diagnostic and preserve any committed reservation. Existing post-send INSERT logging is removed from this sender because its exact log already exists before sending.

No additional migration beyond PR #283 is added in this increment. The required chain remains log compatibility, retry claims, then initial-claim kind. Never deploy only the endpoint without the shared helpers/migrations. Historical rows are not scanned/replayed, provider gates/financial holds are unchanged, and non-2xx/timeout claims remain blocked pending independent reconciliation. A database error while forwarding must not be misreported as a bank rejection or refund.

The native MySQL suite additionally checks forwarded-payload evidence mismatches/missing values, exact initial claim persistence, mutual exclusion with generic/admin delivery and durable uncertain completion. Existing actual payload-builder and signature refusal tests are retained. These are fixture/database tests, not a live Paystack request or merchant credit. Concurrent protected senders use the same already-tested unique transaction claim.

Remaining: `verify.php` still sends inside accounting transactions and has not joined this reservation path; it can still race the protected senders. The accounting-commit-to-reservation gap for protected senders is still not a transactional outbox. Email notification is also outside this claim system. No claim of globally exactly-once notification or merchant wallet credit is made.

## Verify-page post-commit delivery — follow-up after PR #284

The browser verification sender now finishes its accounting transaction first. Only a successful commit sets a local delivery-ready flag; lost fulfilment races and accounting failures never dispatch from this path. Merchant lookup/payload building/signing/HTTP are in a separate Throwable boundary with no rollback of committed accounting. This preserves the legacy requested-naira `amount`, requested-kobo alias, money labels and other payload values.

Before sending, it reloads the committed payment/merchant snapshot and checks the legacy amount contract plus common requested/gateway/fee/net/currency/reference evidence via `payhub_verify_payload_matches()`. Validation normalizes a private copy ONLY; the original raw JSON remains the persisted/signed/sent payload, and this increment does not invent receiving-account evidence in the legacy body. It uses the existing shared initial log/claim and completion helpers. All three known initial senders plus the admin retry now compete on the same transaction primary key. HTTPS/TLS and redirect refusal match other protected paths. Claim/migration/transport/completion failures cannot fall back to unclaimed sending or refund/roll back the already committed payment.

No new migration is introduced beyond the existing log/retry/initial claim chain. No historical replay or provider activation. The accounting-commit-to-reservation crash gap STILL exists: this is post-commit protected delivery, not a transactional outbox. Safe recovery requires a reviewed outbox/reconciliation design rather than deleting claims or treating a missing log as proof of non-delivery.

Native fixtures cover legacy amount/currency/fee/reference mismatches, unmodified body persistence, initial-versus-admin exclusion, refusal inside a caller's accounting transaction, and shared completion. Source-order tests pin commit -> readiness flag -> protected dispatch -> HTTP and the isolated no-rollback delivery boundary. Existing actual payload-builder/signing tests remain. These are not full browser-to-provider settlement or physical/live acceptance tests.

## Verify-page transactional outbox increment

For a newly fulfilled browser-verification payment with a configured merchant webhook URL, the exact legacy payload is now constructed and enqueued in `webhook_outbox` BEFORE accounting commit, using the SAME PDO connection/transaction as the payment and ledger. The helper requires an already active caller transaction and InnoDB transactions/users/ledger/outbox storage; it never commits/rolls back the caller. An event insertion/schema/evidence failure propagates so the caller rolls accounting back rather than committing without the required event. The browser's local fulfilment status becomes pending on that failure, not a false completed local fulfilment. This does not mean the upstream bank refunded or rejected the payment.

Apply operator-only `install/20261118_webhook_outbox.sql` after the existing log/retry/initial-claim migration chain, before the updated helpers/pages. There is no runtime DDL. All protected initial sends now require the outbox table (even non-outbox producers) so a queued event cannot be bypassed by a different payload. Existing logs/claims/events are not backfilled/deleted/relabelled. Missing storage is fail-closed and must be rehearsed before rollout.

The immutable outbox contains producer, exact body, body/snapshot/destination/mode-key SHA-256 bindings and creation time; no raw signing key or full endpoint is stored. The complete named payment snapshot is hashed with normalized PDO scalar types. No webhook URL means no notification configured and no event is enqueued. Missing/malformed notifier credentials/destination do not erase an otherwise valid accounting event: the event is retained with its original configuration binding, while delivery still requires valid current HTTPS/signing configuration. Config repair or changed payment snapshots do not silently retarget an old event; independent reconciliation is needed. A maximum 60,000-byte JSON event fits the existing eventual TEXT delivery-log contract.

Every protected initial sender checks for a queued event under its existing payment lock. If one exists, only its exact body and unchanged payment/endpoint/mode-key bindings may reserve delivery. A competing generic/forwarding variant cannot substitute another payload, and existing permanent claims still fence all attempted/unknown results. Outbox rows are immutable; state is projected from the shared claim, not a resettable `ready` flag. A post-commit/pre-dispatch crash now retains a durable exact notification for this producer. A crash after reservation remains blocked, never automatically replayed.

Native fixtures exercise real transaction/fixture-ledger/event visibility before/after commit, explicit rollback, injected outbox INSERT failure, exact queued body persistence after a simulated dispatch gap, duplicate-event refusal, payload substitution/destination/key-change fencing and exclusive completion. Missing notifier-key cases preserve the event but refuse network reservation. Existing actual payload-builder/signing tests remain. No provider/merchant HTTP is performed.

Remaining scope: this producer now has an atomic accounting/event record, but no recovery dispatcher or reconciliation/rebinding UI is added. Paystack forwarding, API verification, reconciliation/cron/simulation fulfilment still need their own transactional enqueue integrations; their post-commit gaps remain. Recovery tooling must dispatch only verifiably never-attempted events through existing claims, bind producer/version/snapshot and remain opt-in; it must never reclaim uncertainty. No live send, cron activation, provider activation, historical credit or hold release occurs here.

## Paystack transactional enqueue follow-up

Paystack fulfilment now constructs its existing merchant payload and enqueues it before the same accounting/ledger transaction commits, when that merchant has a configured webhook URL. The post-commit sender consumes those original bytes rather than rebuilding a different event. The common enqueue implementation has a fixed producer allowlist (`browser_verify`, `paystack_forward`) with the appropriate legacy/common money-evidence validator; duplicate transaction events still refuse overwrite. No additional schema migration beyond the outbox migration is needed.

A previously swallowed Paystack accounting exception could fall through to the endpoint's final HTTP 200 even though local fulfilment had rolled back. Accounting/outbox exceptions now roll back an active transaction, emit a non-sensitive diagnostic, and exit HTTP 503 so the upstream provider is not falsely told the uncommitted event was processed. This is not a merchant retry or a wallet credit: upstream redelivery must still pass signature/mode and atomic fulfilment checks. An ambiguous commit may already have committed payment+event; a later upstream request cannot fulfil that transaction twice, and the persisted event remains for reconciliation/recovery. Missing/malformed notifier credentials retain queued evidence as in the verify producer; no configured URL means no configured notification.

The shared permanent delivery claim, immutable body/payment/endpoint/key bindings and non-2xx uncertainty policy are unchanged. New native fixtures run test/live Paystack enqueue rollback/commit and injected event-insert failures, exact payload persistence across a simulated dispatch gap, original mode signing, payload substitution refusal and blocked uncertain outcomes. Source-order assertions pin enqueue -> accounting commit -> protected claim -> HTTP, and ensure the failure branch cannot reach final HTTP 200. These tests perform no Paystack/merchant calls.

Still not universal coverage: API verification, reconciliation, cron and simulation fulfilment paths that only call the generic sender after commit need atomic enqueue integration. No automatic outbox dispatcher or reconciliation/rebinding UI is enabled. Do not replay historical payments, reset claims or infer absence of a log proves no credit.
