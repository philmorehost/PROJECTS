# App security question loading and tenant channel policy

The mandatory Android unlock screen could be deadlocked by KYC confinement: `security-quest.php` called an authenticator that applies compliance route restrictions, while the recovery allowlist omitted that endpoint. The response used `message` on an HTTP error; Android only read the success-body `desc`, producing a generic unable-to-load notice. This is a reproducible code-path cause, not a claim that the screenshot alone proves the installed server/build's exact failure.

Both editions now allow this exact security recovery path during KYC confinement. No purchase/transfer route is added. The endpoint authenticates the persisted, vendor-scoped first-party app session directly rather than converting to a merchant API key and performing a second legacy lookup. Inactive/revoked/restricted/account-type rules remain in the shared authenticator. Missing/empty question catalogue returns an explicit support error; nothing bypasses authentication on request failure. Reset verifies the current password with the shared modern/legacy verifier, validates question ids, and writes both fields in one prepared tenant+user-scoped update. Answer mutations are throttled. This retains the legacy answer-storage contract; hashed-answer/session-unlock redesign is not claimed.

All three Android brands now display server `message`/`desc` errors, offer sign-in after HTTP401, refuse empty catalogue/question UI, and leave the gate only after authenticated success explicitly returns `enabled:false` (or normal successful verification/setup). Transport failures never count as a disabled policy. Existing local idle-lock timestamps remain; this increment does not implement server-enforced mobile unlock grants. Existing iOS clients do not have this Android LockActivity; new native iOS lock UI is not added here.

## bc-admin controls

Account Settings → security section → **Security question — Web / App** contains independent ON switches. Default/malformed/unavailable policy is ON for both. The tenant-scoped `sas_settings.security_question_policy` is read fresh; other tenants are unaffected. No saved questions/answers are erased. Save requires CSRF, current password, PIN, mandatory authenticator/email step-up, explicit OFF-risk acknowledgment, fresh credential/status checks, transactional storage and readback; demo restrictions apply. A policy-specific OTP cannot be used for another purpose. Action-channel preferences cannot turn off verification of this policy change.

Web redirect enforcement and direct SecurityQuest access honor only the web switch. All web question forms now carry CSRF. The API returns the app switch only after session authentication. Updated apps are required to recognize disabled state; old installed builds need a coordinated rollout. Questions toggled OFF do not bypass PIN, OTP, KYC, account restrictions or financial holds. Toggling back ON takes effect at the next security-screen fetch/web request; there is no push-forced interruption of an already unlocked native session.

## Acceptance

Contracts cover defaults, independent settings, fresh reads, tenant isolation, recovery-only KYC allowlist, authenticated disabled handling, privileged-save requirements and scoped writes. Disposable MySQL tests execute the actual endpoint dispatch and prepared-query helpers against catalogue/setup/verify/reset fixtures (modern-password verification is a controlled double), duplicate usernames across tenants, independent policy rows and missing catalogue. Shared token and compliance tests remain separate evidence, not a live-device test.

CI Android compilation and physical-device acceptance, the installed host's actual catalogue/database and reverse-proxy Authorization forwarding must be checked before rollout. Never fall back to personal API-key authentication if a proxy strips Authorization; fix its configuration and sign in again. No deployment or financial activation is performed by this change.
