# Protected polling conflict review

The existing platform custody page adds an explicit POST action to open a metadata-only polling conflict report. It passes through the same session-derived Super Admin authority, active/unblocked/password-complete fresh actor lookup, CSRF, PIN, replay-protected authenticator and sensitive-action throttle as other custody actions. Vendor/standalone mutations remain denied. Internal role arrays are not authentication.

The report is rendered only on the no-store POST response in the existing escaped protected evidence panel; it is never put in redirects, session flashes or logs. It is NOT a human receipt for opening/decrypting the underlying evidence, and cannot be used to approve custody. Raw addresses, txids, amounts, credentials, cursors, ciphertext and lease tokens are not selected. Hashes remain sensitive correlation metadata.

Reports show at most fifty sightings for the selected custody account/environment, ordered deterministically by stream creation descending, stream ID, checkpoint revision descending and record hash. This is stream/checkpoint order, not provider event time or global sighting chronology. A fifty-first row sets `truncated`. For each sighting up to ten competing record/transfer hash pairs are shown; an eleventh sets `competing_pairs_truncated`. There is no claim that an untruncated report proves complete provider history. Historical pages predating the overlap index remain absent; no backfill occurs.

Each sighting retains its original first/repeat/changed/conflict classification, exact encrypted page evidence digest, normalized snapshot hash and pinned custody revision. `current_conflict` is separately calculated from current competing associations, so an old first_seen row is visibly conflicted after a later alias appears. No underlying classification, association or evidence is rewritten. Conflict presence does not prove fraud; absence does not prove risk clearance or ownership.

The current custody revision/environment must still match at report time. A custody lock serializes reporting with checkpoint writes; current locking reads avoid repeatable-read stale-snapshot mistakes. Review intentionally does not need active provider credentials, custody approval or encryption keys: operators must be able to investigate stopped/expired/rotated contexts. Supporting transactional schema is still required. Account/environment scope cannot be overridden with a posted stream or cursor. The report is bounded, though large production histories still require query/index/retention performance review before deployment.

A new additive InnoDB `sas_crypto_v2_poll_review_events` table records actor, scope, current custody revision, SHA-256 of the exact returned report JSON and access time. It stores no report body. Audit and report snapshot are committed before any report is returned. Audit failure rolls back and discloses no report. This is application-level access audit, not off-host immutable audit or a retained full report snapshot. The explicit CLI installer now includes **24 production tables**; requests never create/repair schema. No production migration/deployment was performed.

## Safe investigation/recovery

1. Select the account/environment and open a fresh stepped-up report. Check truncation; do not assume all conflicts are visible in a truncated report. There is no pagination or export in this increment.
2. Use a referenced evidence digest in the existing separately stepped-up audited evidence viewer to inspect the encrypted provider page. The metadata report itself does not decrypt evidence or create an evidence-view receipt.
3. Use existing explicit Stop on a selected stream if collection should halt. Stop is revisioned, fences in-flight commits and remains available with stale custody/config/keys. Refresh stale forms instead of replaying old revisions.
4. Preserve conflicting pairs and evidence. Do not delete/reset cursors, reinterpret changed amounts/statuses as credit permission or manufacture a replacement identity. Replacement collection, if required, is a separately explicit fixed-window stream under current approvals, not a continuation/completeness claim.

There is intentionally NO resolve/approve/ignore conflict action, no manual cursor reset, evidence deletion, settlement release, automatic rollover, scheduler or wallet mutation. Future resolution needs a reviewed evidence/independent-approval policy and immutable decisions, not a button that erases identity history. Existing financial holds and withdrawal containment remain unchanged.

Validation extends mocked management boundaries with six posted override refusals and native disposable tests for bounded output, current conflicts, exact report-hash audit, wrong environment/revision/role refusal, audit-failure nondisclosure, nested transaction refusal and unchanged financial tables. Existing parser/transport/stream/lease/overlap suites still apply. No live provider or browser/device verification is claimed.
