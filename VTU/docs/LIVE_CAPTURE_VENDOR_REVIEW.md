# Camera capture and vendor compliance review

## Implemented scope

Both web editions use the same camera-only widget for customer KYC and vendor Account Settings. Photos come from getUserMedia → canvas → JPEG (long edge ≤960 pixels, quality0.78); videos from MediaRecorder (640×480 requested, ≤20fps requested, target500kbps video/32kbps audio, eight-second timer). Browser constraints/bitrate are requests, not guarantees. Blob size is checked before attachment. No gallery picker fallback is exposed for these liveness fields; document/ID/address evidence still supports uploads. Denied camera/microphone, insecure context or unsupported formats fail visibly, not by silently accepting a gallery file. Retake, page hide and interrupted capture stop tracks and clear unfinished captures. Cameras start only after an explicit button click.

Web and multipart API handlers enforce ≤512KiB JPEG photos, 160–960 pixels per side, and ≤3MiB MP4/WebM videos. MIME is checked using fileinfo; absence fails closed. Available GD re-encodes photos and strips metadata. Video duration is browser-controlled only; server-side duration/codec inspection/transcoding is NOT implemented. Hard byte caps still apply to alternate API clients. Existing evidence is preserved, not mass recompressed/deleted. Valid replacement uploads return customers/vendors to review rather than retaining a prior approval.

SAAS `bc-spadmin/VendorKYC.php` already provided vendor review: it now includes optional business-registration/CAC and beneficial-ownership uploads, readable only in the authenticated evidence viewer. Review remains a whole-submission approve/reject/revoke decision, not independent per-document decisions. Decisions require existing CSRF and PIN/OTP step-up, an unexpired one-use reviewer/credential-bound ticket, matching rendered vendor/evidence snapshot, independent reviewer email, required KYC evidence and pending status before approval. Atomic InnoDB vendor/document decisions retain reviewer id/time/note. Nontransactional installations fail closed until operator migration. Review emails and security audit are subsequent operations, not part of the decision transaction. KYB attachments do not automatically establish registry validity, ownership, a separate KYB certification, or product eligibility. No NON-SAAS superadmin area is invented.

Android DG7/JIKABIZ/MZEEVTU KYC selfie selection is changed from gallery to full-size camera intent with permission handling, scoped FileProvider cache, image orientation correction and bounded JPEG downscaling. Native Android build/device acceptance is still required. These native forms do not add a new video recorder in this increment. Existing iOS KYC views provide identity/AI flows rather than the web multipart capture controls; native iOS media/video parity is NOT claimed complete. Older native clients sending large/uncompressed or non-JPEG selfies will be refused by the new server contract and need a coordinated client rollout.

## Trust boundary and remaining acceptance

Camera UX and a posted file do NOT prove real-time biometric liveness, identity, capture origin or anti-replay. API callers can synthesize files and virtual cameras can replay media. No client boolean is treated as proof and no automatic approval is added. Reviewed evidence remains manual compliance evidence. Verified liveness requires an approved challenge/attestation/provider pipeline and device/security acceptance; this change does not implement that pipeline.

Browser tests simulate photo/video, permission denial, unsupported context, cancellation and oversize rejection; they are not physical-device evidence. Native MySQL tests cover stale evidence, missing requirements, self-review, rollback after injected document-write failure, durable reviewer attribution, replay, reason-required rejection and transaction/engine refusal. Media boundary and ticket tests supplement them. Still required: real HTTPS Android/iOS/Safari camera/microphone tests, native builds, low-memory/slow-link tests, operator limits/storage configuration and review/compliance acceptance. No deployment, automatic vendor activation or financial-provider activation is authorized by this increment. All financial holds remain. Provider execution/reconciliation work remains separate.
