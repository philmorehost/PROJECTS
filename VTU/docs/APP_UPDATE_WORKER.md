# Optional Android update notification worker

## Deployment status and scope

Source implementation only. No worker, cron schedule or environment switch has
been installed/enabled by this change. No live Firebase delivery is verified.
Crypto staging is unrelated and remains paused. This is **not** the SAAS platform
System Update feature, which remains exclusive to bc-spadmin.

Each vendor uses a dedicated Firebase project. Existing Android clients subscribe
to `app_updates`, a project-wide topic, not a device-token queue. The software
rejects projects known to be shared by multiple vendors in this database. It
cannot prove that a project is not reused in another installation.

## Approval and delivery model

1. Deploy the source and the already-required additive dispatch-claim migration
   through the normal authorized deployment process. The worker never invokes
   `bc-tables.php` or creates/migrates tables itself. Do not run database cleanup.
2. Configure a valid Firebase key and a published release in
   `bc-admin/AppUpdateBroadcast.php`. For local APKs the file must be readable,
   at most 256 MiB, inside this installation's `apk` directory, and not a symlink.
   For Google Play only an official HTTPS app-details URL is allowed. URL validation
   does **not** prove that a Play release is published or its package belongs to you.
3. Check **Approve one automatic notification for this exact Android release** and
   save with the required PIN + Google Authenticator/email OTP. The checkbox is
   deliberately unchecked each time. Saving without it removes automatic approval.
4. Approval expires after seven days. It binds release settings, tenant website
   host, Firebase project/stored-key digest, local APK content digest (if applicable),
   and vendor password/PIN/authenticator fingerprints. Changes require fresh approval.
   Keys/passwords are not copied into the approval value or worker output.
5. The worker checks current vendor status, block/forced-password/setup restrictions,
   subscription expiry, dedicated-project setting and approval before sending, then
   checks again after OAuth and immediately at the Firebase message-send boundary.
   These are point-in-time checks; an already in-flight request may finish after stop.
6. Manual and automatic sends share the same durable claim per vendor/Android
   version. No accepted, unknown or interrupted attempt is retried. Changing the
   URL/project or reapproving does not reset a claim. Do not delete claim records
   or bump version codes merely to blindly retry an uncertain message.

## Operator preflight (dry run, no Firebase calls or send claims)

Use the installation's absolute path and its installed PHP CLI binary. From the
installation root, replacing the example vendor ID with the real one:

```sh
php cron/process_app_updates.php --help
php cron/process_app_updates.php --vendor=7
```

The default is dry-run even if the environment send switch is present. Expected
outcomes include `not_approved`, `needs_review`, `ready_dry_run`, `already_attempted`
and `unavailable`. The last requires checking configuration/database access;
raw database/provider/credential details are deliberately not printed.

## Optional activation — separate operator action, NOT performed here

Only after approval, deployment review and a successful dry-run, an authorized
server operator may schedule a per-vendor invocation with BOTH the `--send` flag
and `BC_APP_UPDATE_WORKER_ENABLED=1` in that CLI process's environment. There is no
HTTP trigger. The worker handles one vendor per invocation, no unbounded drain.
Use your scheduler's normal non-overlap/logging controls. Overlapping invocations
also share the database's unique release claim, so they cannot both send a release.
OAuth and Firebase connections are bounded (5-second connect, 15/20-second totals),
with a 60-second soft pre-send freshness budget; a request already started may
finish after that budget. No cron is installed automatically and no environment
file is generated by this implementation.

## Stop and investigate

Remove automatic approval through its independently verified stop form, disable
the scheduler and remove/disable the server send switch. Old claims remain intact.
If removal cannot be confirmed, stop the scheduler/switch immediately. Environment
changes affect new processes, not a request already in flight.

`accepted` means Firebase accepted a named message, **not** guaranteed delivery or
installation. `unknown`/`dispatching` must be investigated in Firebase logs. The
system guarantees at-most-one local message transport attempt while durable claim
records remain intact, not exactly-once device delivery or protection after database
restore/loss. No automatic retry/reclaim/recovery reset is provided.
