# Read-only tenant service reconciliation view

Both editions expose **bc-admin → Settings / System Function → Service Reconciliation (read only)**. The authenticated vendor id is the sole scope; no request parameter selects a tenant. This is an operational projection of intake requests and the held attempt journal, not a dispatch/financial administration screen. No write form, POST action, retry, release, approval, debit/refund/settlement, provider call or automatic journal registration exists here.

The list shows up to50 requests with keyset pagination, including intake without a journal record. Missing journal entries never imply failed execution. Details show the latest100 observations, explicitly flagging omitted older records. A consistent InnoDB read-only REPEATABLE READ snapshot keeps request/journal/event projections coherent under concurrent writes. Existing caller transactions and nontransactional/missing storage are refused rather than implicitly committed. Runtime handlers contain no schema DDL. Unavailable storage returns503 with an operator message, not an empty success view. Cross-tenant/nonexistent request detail returns the same404. Non-GET methods return405.

The display distinguishes intake status from journal observations and settlement proof. Alerts identify changed provider/owner and any stale/conflicting event disposition. This projection does not recompute the full payload fingerprint; journal writes independently do that. Alerts are not exhaustive compliance or fulfilment verification, and an absent alert is not clearance to execute. Only opaque intake references, service/provider labels, intake/journal state, version, receipt disposition/outcome and database timestamps are exposed. Raw payloads, usernames, provider idempotency keys, provider references, evidence digests and observation hashes are deliberately excluded. All dynamic fields are HTML escaped; responses are private/no-store.

## Operator prerequisites

Apply the base `20261118_service_attempt_journal.sql` migration, then apply `20261118_service_attempt_review_indexes.sql` ONCE using versioned operator migration tooling outside application transactions. The latter adds tenant/request keyset and receipt-review/timeline indexes. Plan backups, capacity and locking/DDL impact for large tables before migration; the UI neither builds indexes nor changes engines automatically. No historical records are deleted or reclassified. Standard authenticated bc-admin vendor-account access controls remain; a separate delegated-reviewer RBAC/step-up policy is not introduced by this read-only increment.

## Evidence and limits

Contracts check tenant predicates, strict reference parsing, bounded reads, GET-only routing, no mutation forms, private headers, shell navigation and warning wording. Render fixtures exercise adversarial values, list/detail/empty/unavailable states, truncation labels and responsive table markup. Both editions' native MySQL tests exercise scoped projections, private-field exclusion, missing-journal intake, keyset pagination, bounded event timelines, conflict alerts, outer-transaction preservation and missing-schema refusal. Native tests run against synthetic records, not live provider data. Physical/mobile visual acceptance is separate from HTML render assertions.

This page does not create a trusted provider-ingress path, authenticate evidence, enable dispatch or complete a provider-backed service. Merchant/product/currency eligibility, verified polling/webhooks, secured raw-evidence retention, lease/crash recovery, operational exception resolution and authorized settlement remain pending. Existing financial holds remain; no deployment or provider activation is performed.
