# Vendor registration controls and verification

## Operator use

SAAS: **bc-spadmin → Manage Vendors → Vendor Signup Security**, or `bc-spadmin/VendorRegistrationSettings.php`. The same link is on Global Service Control and Pending Registrations. Vendor signup has its own ON/OFF setting, separate from customer registration. Missing setting preserves ON for compatibility, but mailbox verification is mandatory for every new application. OFF returns503 for the public page/POST and refuses code sends/completions. Existing vendors and login are not disabled. Save requires fresh active owner identity, POST/CSRF, demo refusal, rate limiting, PIN and configured action verification (existing platform-owner authenticator enrollment rule applies). Old codes are invalidated on every policy save.

## Mailbox / abuse defenses

Public VendorReg requires strict scalar/length validation, a12–72-byte password (raw password hashed; not HTML/SQL-transformed), valid phone/package/payment input, CSRF and a honeypot. Email addresses are bounded ASCII, syntactically validated and normalized without silently stripping hostile input; domain literals, malformed domains, common temporary-mail domains and configured blocked domains/subdomains are refused. An MX-capable domain is required; null MX/DNS lookup failure refuses intake. This deliberately does not certify a mailbox or guarantee a complete disposable-mail database.

Ownership requires a random six-digit email code, hashed at rest, browser-bound, address-bound and policy-epoch-bound. Codes expire after10 minutes, allow at most5 guesses, and are single-use through an InnoDB row lock/transaction. Resend removes the previous browser challenge. SMTP must use configured platform credentials, not tenant-selected credentials; delivery failure leaves no usable new code. Persistent rate limits are serialized by MySQL advisory locks:5 sends/IP/15 minutes,3/address/15 minutes,100/platform/15 minutes and20 verification attempts/IP/15 minutes, plus30 public POST attempts/IP/15 minutes before DNS lookup. Raw IP comes only from REMOTE_ADDR; untrusted forwarded headers are not used. These application limits supplement, not replace, a hosting/WAF rate limit.

The old `web/WebsiteOrderRequest.php` direct active-vendor insertion is removed: SAAS redirects to verified intake; NON-SAAS returns410 because the single-owner edition must not create extra public vendors.

## KYC / KYB

Existing platform `force_kyc` and enabled `sas_super_admin_kyc_verifications` are read fresh, not from option caches. Vendor KYB can be required on the new security page; an existing `force_kyb=1` is also honored. KYB applications require registered business name/registration number. Mailbox verification and payment NEVER satisfy KYC/KYB.

In Pending Registrations, use **KYC / KYB review** only after completing all configured checks through the approved secure verification process. Record completed KYC/KYB case references, confirm evidence review and supply PIN/action verification. Do not place raw ID numbers or documents in case-reference fields. This is an explicit manual review checkpoint, NOT a newly integrated automated identity provider or public document-upload service. Review is bound to the applicant identity and required-check snapshot; identity or policy changes invalidate it. Approval refuses missing mailbox proof and required unreviewed compliance, even if paid. Completed proof/reviewer/case references and business details are copied to the vendor's onboarding record before the old pending row can be removed. A completed required KYC review initializes vendor KYC status as verified; no user-controlled approval flag is accepted.

Legacy pending rows are NOT silently treated as mailbox verified. They remain blocked and require controlled support remediation/resubmission; do not delete payment/audit evidence merely to clear a duplicate. Existing active vendor KYC enforcement is unchanged. Closing signup does not cancel paid applications already in the manual review queue.

## Deployment and testing boundaries

Additive schema version `2026.11.18-vendor-registration-1` adds hashed challenges, pending mailbox/business/review fields and vendor onboarding proof fields. No existing vendor/history is removed by migration. Settings require transactional InnoDB options storage; compliance review requires InnoDB pending-application storage. Before rollout confirm TLS/SSL-configured platform SMTP delivery, production DNS/MX resolution and the operator's secure KYC/KYB process. Email/domain validity does not prove lawful identity; legitimate mailboxes can still be abused.

Tests: pure boundary contracts plus disposable MySQL code expiry/guess limits/address+browser binding/resend/replay, concurrent single consumption, policy toggles/epoch revocation, real SQL entitlement policy reads, mail-failure refusal and persistent send limits. Mail/factor/demo/security-DDL are explicit doubles in storage tests; no real email, verification provider, deployment or live financial activation is performed.

## Server invoices, payment channels and daily limits (follow-up)

Root cause confirmed in source: public registration used the posted `total_amount` when initially saving an application. Manual deposits never recalculated it; the old online recalculation also omitted fixed APK/iOS/Play Store/SMS Bridge charges. A Paystack success callback previously trusted metadata without matching the saved invoice amount/currency/customer/reference. The screenshot is evidence of suspicious/incorrect records, not attribution or proof of successful unauthorized approval.

Both channels now freeze an integer-minor-unit NGN invoice BEFORE saving. Its plan must exist, have a positive configured price and positive duration. Every selected fixed option, dynamic add-on and registrar-priced domain is included; unknown/unpriced/malformed selections refuse intake. Browser amount/fees cannot determine the invoice. Stored billable fields and payment evidence must match the snapshot before approval. Existing zero/negative or snapshot-less records remain blocked, not silently repaired/deleted. Quoted records cannot be edited through Edit Vendor Order. Plan-price changes do not rewrite an already-issued invoice; approval uses the quoted duration and records the actual invoice total.

**Payment policy:** Vendor Signup Security offers **Online only** (secure default) or **Online and manual deposit**. Both have the same invoice validation. Manual confirmation requires the already verified platform-owner action, an exact cleared NGN amount, unique bank statement reference and explicit cleared-funds attestation; it is audited. Uploading an image alone is not payment proof. Online registrations cannot be marked paid through the manual button. The Paystack callback accepts only a server-verified successful transaction matching the stored random reference, exact amount/currency, customer email and registration metadata. Receipt references cannot be reused; verified replay does not provision anything or activate an account. The registration callback no longer registers domains; hosting/domain actions remain after gated approval. No new online provider is introduced.

**OTP first:** The full registration form is rendered only after successful mailbox-code verification. Backend POST checks the same durable browser/address/epoch-bound proof, which is consumed once atomically with application insertion. No form field can substitute for the server proof. The code/session proof still expires 10 minutes after issuance.

**One website per rolling24 hours:** email, normalized phone and a persistent random HttpOnly/Secure/SameSite=Lax browser identifier are hashed and reserved in the same transaction as the application. Changing IP alone does not reset these limits. Duplicate email checks/unique constraints also continue across pending/active accounts. Failed insertions roll back quota claims and proof use. This is a browser identifier, NOT an undefeatable physical-computer fingerprint: clearing cookies, another browser or a new device can evade that key. Verified email and phone-key limits remain, but without verified phone ownership a person can supply another plausible number. Do not claim physical-device or real-person uniqueness.

**Phone/address/domain truth:** Nigerian mobile prefixes and international E.164 formatting are checked/canonicalized and obvious dummy patterns refused. This does NOT prove SIM ownership, reachability or WhatsApp membership. A supported, reliable free automated WhatsApp-number lookup is not supplied; use an approved verification provider or explicit manual WhatsApp ownership review if required. Names/physical addresses have stronger structural checks, but real identity/address truth still requires KYC evidence. Existing domains now require control of a browser-bound `_vendor-verification` DNS TXT token before submission; newly purchased domains retain server-side registrar availability/price checks. DNS TXT/MX failures fail closed. Domain ownership is not proof of lawful business identity.

Approved and declined applications are now archived using status1/status2 instead of deleting their underlying evidence; the actionable queue and decision lookups require status0. Archived email/domain uniqueness remains in force and resubmission needs controlled support remediation.

No deployment or live database repair, payment, SMTP, registrar or WhatsApp call was performed. Validate the complete email→TXT/new-domain→quote→sandbox payment→compliance→approval journey in the deployment environment before opening registration. Existing suspicious or paid applications require controlled reconciliation; never mark them verified merely to make the queue disappear.

Additional independent-of-IP abuse limits: persistent-browser code sends are limited to5/15 minutes, and verified-mailbox/browser final submission attempts to10/24 hours before expensive registrar/TXT processing. Configure trusted reverse-proxy IP restoration at the web server if applicable; never trust arbitrary forwarded headers.
